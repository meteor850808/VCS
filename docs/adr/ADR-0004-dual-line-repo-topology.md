# ADR-0004 — 仓库双线拓扑：远端 `main` 是发布镜像，本地 monorepo 是开发主线

- **状态**: 已接受（2026-11-11）
- **决策者**: VCS 空间质检维护者
- **上下文**: 同一个项目存在两种目录布局。开发机上它是 monorepo 的一个子目录
  （`空间质检/app`、`空间质检/tests`），远端仓库 `meteor850808/VCS` 的 `main` 是单项目
  根布局（`app/`、`tests/`、`alembic/` 直接位于仓库根）。两条历史**没有共同祖先**，
  无法直接 merge/rebase 对齐。需要明确哪条线是权威，否则每次发布都要猜。

## 关键事实（取证，2026-11-11）

1. **无共同祖先**：`git merge-base origin/main feat/quality-scoring-v3` 与本仓
   `main` 均以退出码 1 结束（无输出）；`git merge-base` 找不到任何公共提交。
2. **布局差异是结构性的**：`git ls-tree --name-only origin/main` 直接列出
   `app`、`alembic`、`tests`、`Dockerfile` 等；远端树中不存在 `空间质检` 这一层目录。
3. **提交量差异大**：`origin/main` 可达 28 个提交，monorepo 开发线可达 158 个。
   发布镜像只承载「已验收的发布内容」，不是开发历史的镜像。
4. **本地 `main` 属于 monorepo 线**（`1e96b73`），与 `origin/main` 无关系；
   把本地 `main` 指向 `origin/main` 只会让两条线互相污染。
5. **发布验证已可重复**：在根布局工作树上对 `release/main`（跟踪 `origin/main`）
   跑全量测试得到 `1843 passed / 9 skipped`，与端口分支同形；说明「远端树 = 可发布物」
   这一假设可以用测试实证，而不是靠声明。

## 决策

**采用双线拓扑，两条线职责互斥：**

| 线 | 位置 | 角色 | 允许的操作 |
|----|------|------|------------|
| 开发主线 | 本地 monorepo 工作树（`feat/*` 分支） | 唯一开发入口；历史完整、含 monorepo 其他项目 | 日常提交、TDD、跑全量测试 |
| 发布镜像 | `origin/main`，本地以 `release/main` 跟踪 | 只承载已验收的、根布局的可发布树 | 只接受经端口流程（ADR-0005）带入的提交 + PR 合并 |

铁律：
1. **不覆写**：不以本地 `main` 强制推送 `origin/main`，不做历史改写。
2. **不改布局**：发布镜像的根布局是既定契约（`Dockerfile`、`docker-compose.*.yml`、
   `alembic.ini` 都按根布局写路径），不为了「与 monorepo 一致」而迁移。
3. **端口而不是合并**：内容从开发主线到发布镜像，一律走 ADR-0005 的单提交端口流程。
4. **发布镜像可独立验收**：任何「发布镜像没问题」的结论，必须在根布局树上跑过测试。

## 替代方案与权衡

| 方案 | 说明 | 结论 |
|------|------|------|
| A. **双线 + 单向端口** | 各自历史自然生长；内容用补丁单向往上搬 | ✅ 采纳 |
| B. 把 monorepo 子目录提升为独立仓库（`git subtree split`） | 理论最干净，可 `git push` 单线 | ❌ 否决赛：本机非 ASCII 前缀（`空间质检`）实测失败，无法稳定复现 |
| C. 把远端改成 monorepo 布局（加一层 `空间质检/`） | 单线、无端口成本 | ❌ 否决：破坏既有 `Dockerfile`/compose/alembic 路径契约，且需重写 CI 全部工作目录 |
| D. 用 `git replace` / `filter-repo` 把两史拼接 | 单线、保留历史 | ❌ 否决：改写历史，与「不改写、可审计」的原则冲突 |
| E. 直接 `git push --force` 本地 `main` 覆盖远端 | 最省事 | ❌ 否决：两条线无共同祖先，会销毁发布镜像历史 |

## 后果

- **正面**：开发历史不被发布节奏绑架；发布镜像始终是「能直接部署的根布局」；
  端口产物可逐条审计（每条补丁 = 一个开发提交）。
- **负面/权衡**：同一改动存在**两个提交哈希**（如 `7dcd79a` → `54a18b0`），
  追溯需同时记录两侧；端口是额外一步人工/脚本动作，漏端口会造成「已修但未发布」。
- **监控**：`origin/main` 与开发主线的差距必须显式可见——发布前对
  `release/main` 跑全量测试是当前唯一的自动守卫；后续可加「端口清单」比对
  （开发提交清单 vs 已端口提交清单）。

## 触发重评估条件

1. Git 侧能稳定支持非 ASCII 前缀的 `subtree split`（或项目目录改为 ASCII 名），
   且 `merge-base` 仍为空——此时 B 案重新变得有吸引力。
2. 发布镜像需要承载第二个项目（即天然变回 monorepo）。
3. 端口漏搬导致线上缺陷——说明单向往上搬需要自动化（CI 校验端口清单）。
