# ADR-0005 — 跨布局端口流程：`format-patch` 单提交 + `am -p2 --3way`

- **状态**: 已接受（2026-11-11）
- **决策者**: VCS 空间质检维护者
- **上下文**: 按 ADR-0004，开发内容要从 monorepo 子目录（`空间质检/…`）搬到根布局仓库
  （`…`）。两条历史无共同祖先，且路径相差一层。需要一条**可重复执行**、不写历史、
  能保留开发提交意图的搬运流程；没有流程就只能靠手工重打补丁，必然出现「改了 A 漏了 B」。

## 关键事实（取证，2026-11-11）

1. **路径差恰好一层**：开发侧 `a/空间质检/app/api/v1/convert.py`，发布侧需要
   `a/app/api/v1/convert.py`。`git am -p2` 剥离前两层正好命中。
2. **必须限定路径**：`git format-patch <commit> -- <path>` 只导出该子目录下的改动。
   不加路径限定会把 monorepo 里其他项目的改动一起导出（本仓主工作树有大量无关未提交改动）。
3. **单提交端口可重复**：本轮连续两次执行同一流程，均一次成功——
   `5a0f030`（convert 修复）与 `54a18b0`（归属列收敛，源提交 `7dcd79a`）。
   两次都在 `am` 后直接跑全量测试通过（`1854 passed / 9 skipped`）。
4. **`subtree split` 不可用**：本机 `git subtree split --prefix=空间质检` 因非 ASCII
   前缀失败，故不能走「拆成独立历史再 push」的捷径。
5. **补丁文件名为 ASCII slug**：中文提交标题会被转成 `0001-fix-api-owner_id-Key-ID.patch`
   这类名字，脚本不能假设文件名等于标题，需 `Get-ChildItem` 取实际名。

## 决策

**每次端口只搬一个开发提交，流程固定为四步：**

```bash
# 1) 开发侧：单提交导出（限定子目录，不加 --numbered 便于重复执行不撞号）
git format-patch -1 <commit> --no-numbered -o <patch_dir> -- 空间质检

# 2) 发布侧：在跟踪 origin/main 的工作树上开分支
git checkout -b <topic> release/main

# 3) 应用（-p2 剥掉 a/ + 空间质检/；--3way 允许上下文漂移）
git am -p2 --3way <patch_dir>/<actual-filename>.patch

# 4) 验收（在根布局树上，必须做）
pytest tests/ -q --no-cov
```

约束：
1. **一提交一补丁**，按开发侧提交顺序依次应用；不合并、不 squash（保证每条都能反查）。
2. **端口后必须跑全量测试**——`am` 成功只证明文本能贴上，不证明行为等价。
3. **提交信息保持原样**（`am` 默认保留作者与信息），不追加「ported from…」噪音；
   两侧哈希对照记在 PR 描述里。
4. **不改写历史**：冲突时修工作树后 `git am --continue`，不许 `push --force` 到已发布分支。

## 替代方案与权衡

| 方案 | 说明 | 结论 |
|------|------|------|
| A. **`format-patch` + `am -p2 --3way`** | 单提交、逐条可审、保留原始提交信息 | ✅ 采纳 |
| B. `git diff | patch -p2` 应用工作树改动 | 丢失提交信息与作者，无法逐条追溯 | ❌ 否决 |
| C. 手工复制文件再提交 | 与开发提交脱钩，无法证明「搬的是同一份」 | ❌ 否决 |
| D. `git subtree split` / `filter-repo` 造共同历史 | 一次到位，之后可 merge | ❌ 否决：非 ASCII 前缀在本机失败；且改写历史 |
| E. 在发布侧重新实现一遍改动 | 双份维护、行为易漂移 | ❌ 否决 |

## 后果

- **正面**：端口成为机械动作，可脚本化、可重复；每条补丁与开发提交一一对应；
  冲突局限在单个提交（`--3way` 让上下文漂移可自动消解）。
- **负面/权衡**：同一改动两个哈希，需要 PR 描述留对照表；提交数线性增长
  （本轮 15 + 7 + 1 条补丁）；`am` 与 `pytest` 都必须人工/CI 执行，漏一步就失去保证。
- **监控**：CI 在 PR 上跑 test / prod-config / smoke 三组作业，是端口正确性的自动守卫
  （本轮 PR #1 与 #2 均以三组全绿为合并前提）。

## 触发重评估条件

1. 端口冲突从「偶发」变为「每次都有」——说明两条线的公共部分在分叉，应回到 ADR-0004 重选布局策略。
2. 单次发布需要端口 20 个以上提交——手工逐条成本过高，需引入补丁队列/自动端口脚本。
3. Git 支持非 ASCII 前缀的稳定 `subtree split` —— 可改用单线历史 + merge。
