# ADR-0003 — 知识图谱采用纯视图（ORM → nodes/edges），不引入图数据库

- **状态**: 已接受（2026-09-30）
- **决策者**: VCS 空间质检维护者
- **上下文**: v2.22.1 §⑤ 留档的「知识图谱」调研项需要落地。本仓模型本已是一张图
  （standard → 层组(自引用, 深度≤5) → 表 → 字段；字段 N:M 字典；表 N:M 层组(S9)），
  问题是：直接从 ORM 出图（纯视图），还是引入 Neo4j 等图数据库？

## 关键事实（取证，2026-09-30）

1. **图深度是常数**：`MAX_LAYER_DEPTH = 5`（`_common.py:33`，4 个端点强制）；
   全仓 `WITH RECURSIVE` 0 命中 —— 现有 `selectinload` 链 + Python 循环已够用。
   图数据库的核心卖点（变长路径）在此无用武之地。
   真实参照物（一厅八室五标准）层组深度实测**全部为 2**。
2. **双写面横跨全部写路径**：写入口分布于 standards/layers/tables/fields/
   dictionaries/field_links 六组 CRUD + `structure_analyzer` 自动建层 +
   `source_data`/`data_standards` 两条旧 API 旁路（20+ 处）；且 `update/upsert`
   导入走 `_delete_standard_children` **全删重建**。图库需同步挂进 API 层
   58 处 commit 点（ADR-0002），漏一处 = 图谱静默失同步 —— 画出一张国期图。
3. **架构方向冲突**：v2.22.3 刚确立「PG 是唯一真源、连接键是语义编码而非
   服务端 id」（CSV A2-1 归档整批围绕此原则）。图数据库 = 第二真源，
   与刚建立的单一真源方向相反。
4. **规模不需要**：单标准节点量级 = 层组 + 表 + 字段 + 字典 + 条目，真实最大
   （SHGT_SURVEY）255 表 / 3288 字段 / 187 字典 / 2031 条目 —— PG 毫无压力，
   但**摘要响应不能带明细**（否则 ~1.5MB），须摘要 + 懒加载两级契约。
5. **无只读副本**：双写只会加重主库（pool 5+15）。
6. **前端零依赖规矩**：不依赖 CDN、全部内联 —— Cytoscape 数百 KB 内联成本高，
   且三列层级布局手写 SVG 即可表达（深度≤5）。
7. **边在当前架构里已易丢**：版本回滚曾丢字段-字典绑定与 S9 次归属
   （2026-09-30 修复，`7ded206`）—— 再加一个需要同步的图存储只会更糟。

## 决策

**采用 A 档纯视图：`GET /{id}/graph`（摘要：nodes + 聚合 binds 边 + 徽章计数）
+ `GET /{id}/graph/nodes/{node_id}`（明细懒加载），前端手写 SVG 三列布局，
不引入图数据库、不引入图可视化库。**

理由：
1. 只读查询，零双写、零新基础设施、零失同步可能。
2. 下游契约已验证：`_layer_tree_options` 深载 + binds 聚合一次查齐。
3. 与 ADR-0002（事务边界）、v2.22.3（单一真源）方向一致。
4. 真实载荷驱动的设计：摘要不含明细，SHGT_SURVEY 级别约 50~100KB 而非 1.5MB。

## 替代方案与权衡

| 方案 | 说明 | 结论 |
|------|------|------|
| A. **纯视图（ORM → nodes/edges + 手写 SVG）** | 零新依赖、零双写；跨标准查询要写 SQL join | ✅ 采纳 |
| B. 纯视图 + 图查询服务（递归 CTE / 跨标准影响分析 API） | A 的超集，按需增量加，不阻塞 | ⏸ A 落地后视需求 |
| C. 图数据库（Neo4j 等） | 变长路径/图算法原生；双写 20+ 入口、第二真源、JVM 运维、与单一真源方向冲突 | ❌ 否决（触发条件见下） |

## 后果

- **正面**：图谱功能当日可用；PG 仍是唯一真源；无同步/备份/运维新增面。
- **负面/权衡**：跨标准影响分析（"改这个 dict_code 波及哪些标准"）需要写
  多表 join SQL，深度增加时代价上升；无内置图算法。
- **已知事实留档**：一厅八室参照物 225 个 dict_code 中 103 个跨标准复用
  （CT4 被 5 个标准全部使用）—— 这批公共代码表天然适合全局字典化，
  是 B 档（跨标准查询）最可能的第一个真实需求。

## 触发重评估条件

出现任一条，重开本 ADR 评估 B/C 档：
1. 层组深度需求放开（如行业标准 8~10 层嵌套）；
2. **跨标准影响分析成为高频操作**（改字典编码 → 波及字段→表→规则的全局追踪）；
3. 标准数量增长到万级且需频繁全局图查询；
4. 出现必须用图算法的需求（中心度找核心字典、社区发现找冗余表）。
