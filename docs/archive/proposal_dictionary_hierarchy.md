# VCS 数据字典父级关联（层级字典）方案文档

- **状态**: 📌 方案存档，**暂不实施**（2026-08-12 决策：字典父级关联暂时不做）
- **版本**: v2.9 后续增强候选
- **关联**: `docs/revision_v2_9.md` §遗留说明-2；`docs/test_manual_v2_9.md`
- **决策原则**: 保留现有扁平字典能力不变，任何方案必须向后兼容（存量数据 + 现有 API + 现有 Excel 往返）

---

## 1. 需求背景

数据字典当前支持「全局字典 / 标准字典」双维度（v2.9 拆分完成），但**字典条目本身是扁平结构**——`dictionary_items.parent_code` 字段仅作记录，无父级存在性校验、无层级约束、不参与质检、Excel 导入导出不携带。用户提出字典条目应有父级关联能力（如「地类」→「一级地类/二级地类」的码值树），但**暂不实施**，先行存档方案。

## 2. 现状盘点（2026-08-12 代码事实）

| 层 | 现状 | 文件 |
|----|------|------|
| 模型 | `parent_code: String(64) \| None`，无外键、无索引、无唯一约束、无父级校验；同字典 `(dict_id, item_code)` 唯一 | `app/models/dictionary_item.py` |
| Schema | `DictionaryItemCreate/Update.parent_code` 仅 `max_length=64`，无存在性/层级校验 | `app/schemas/data_standard_v2.py` |
| API | 批量添加/更新直通落库；`PUT` 用盲 `setattr`（任意 key 可写）；删除条目**无子级保护**（可删有子项的父项）；字典删除级联删条目（FK CASCADE） | `app/api/v1/data_standard_v2.py` |
| 质检 | A5 值域控制取**扁平** `item_code` 集合（`link.dictionary.items` 全量展开），层级不参与 | `app/services/quality/attribute_checker.py` |
| Excel | v2 模板/导出「字典定义」Sheet 列 = 字典编码/字典名称/适用范围/字典项编码/字典项名称/描述，**无父级编码列**；解析器同样不读 | `app/services/data_standard_parser.py`, `app/api/v1/data_standard_v2.py` |
| 前端 | 字典项表格直接展示 `parent_code` 原文列（若填写），无树渲染、无父级选择器 | `app/frontend/index.html` |
| 源数据 | `source_data.py` 字典同样透传 `parent_code`（共用同一 `DictionaryItem` 模型） | `app/api/v1/source_data.py` |

## 3. 方案对比

| 维度 | 方案 A：校验加固（最小改造） | 方案 B：自引用外键（正式层级，**推荐**） | 方案 C：独立关联表（DAG） |
|------|------------------------------|----------------------------------------|--------------------------|
| 存储 | 保持 `parent_code` 列 | `parent_code` → `parent_id` 自引用 FK（迁移保留 code 兼容） | 新增 `dictionary_item_links(parent_id, child_id)` 关联表 |
| 数据约束 | 应用层校验：父 code 必须存在于同字典；禁止自引用；删除父项前检查子项 | DB 层强制：FK + 唯一父/子 + 同字典约束；删除父项 ON DELETE 策略（RESTRICT / 级联改 NULL 二选一） | DB 层强制 + 支持多父（子项可属多个父） |
| 质检 A5 | 不变（仍扁平集合） | **可选增强**：父码值代表整棵子树通配（`code 以父.开头` 命中） | 同 B，但通配规则复杂化（多父取并集） |
| Excel 往返 | 模板加「父级编码」列 + 导入校验 | 模板加「父级编码」列（导出按树前序排；导入两遍法：先建全部项再建父子） | 同 B（父列用逗号分隔多父） |
| 前端 | 字典项表格加父级下拉/只读列 + 删除保护提示 | 树形渲染（缩进/展开折叠）+ 父级选择器 + 删除保护 | 同 B + 多父多选 |
| 深度/防环 | 应用层自检（最多 N 层 + 祖先链查重） | 应用层自检 + 可选 DB 触发器 | 应用层拓扑校验 |
| 改动量 | 小（API 校验 + Schema + 前端微调） | 中（迁移 + API + 质检 + 前端 + Excel） | 大（新表 + 全链路） |
| 风险 | 仅防脏数据，无法表达真正层级语义 | 标准方案，能力完整 | 过度设计——当前无多父需求 |

### 3.1 当前方案 vs 优化方案（方案 B）：优缺点决策对比

> 本节为「维持现状」与「启用方案 B」的完整权衡（2026-08-12 决策时补充），供将来需求明确时决策复用。

**定位一句话：**
- **当前方案**：`parent_code` 是纯记录列——**"写什么存什么，系统零理解"**。不校验、不渲染、不参与质检、Excel 不携带。
- **优化方案（方案 B）**：自引用外键 `parent_id` + 保留 `parent_code` 双写——**"系统原生理解树"**。DB 强制父子关系，前端渲染树，质检父码通配，Excel 往返保持层级。

#### 3.1.1 数据完整性（差距最大的维度）

| 场景 | 当前方案 | 方案 B |
|------|----------|--------|
| 假父引用（父码不存在） | ❌ 静默接受入库 | ✅ FK 拒绝 |
| 自引用 / 循环引用 | ❌ 静默接受 | ✅ 应用层 400 |
| 深度失控 | ❌ 可无限嵌套 | ✅ 深度 ≤3 限制 |
| 删除有子项的父项 | ❌ 直接删，子项悬空（与 v2.9 清理的"隐身脏字典"同型问题） | ✅ 409 拦截（`ondelete=RESTRICT`） |

> 关键判断：当前方案的缺点不是"缺功能"，而是**脏数据积累**——`PUT` 用盲 `setattr` 导致任何非法 `parent_code` 都能落库，将来一旦启用层级，清洗成本不可控。方案 B 把数据卫生从"靠自觉"变成"靠 DB 兜底"。

#### 3.1.2 业务表达与质检（方案 B 的增值点）

- **当前方案**：A5 值域为扁平集合精确匹配。标准要放行"一级地类 A 下所有二级码"只能穷举 `A01`~`A99`；字典加子码后必须同步改标准。
- **方案 B（P2）**：父码通配——允许 `A` 即自动放行 `A01/A02/…`；字典新增子码质检规则**自动生效**，字典维护与标准规则解耦。这是当前方案给不了的业务价值。

#### 3.1.3 版本快照与回滚（2026-08-12 确认的事实）

- 数据标准版本快照 `_build_standard_snapshot`（`app/api/v1/data_standard_v2.py` L2068-2135）**已携带字典及 items**，版本对比/回滚已覆盖字典项。
- **当前方案**：快照里若填了 `parent_code` 会原样保留，但回滚恢复时同样无校验——坏数据随版本"合法传播"。
- **方案 B**：`parent_code` 双写使快照格式**零改动**天然携带层级；回滚后层级完整自洽，仅多一步"回滚后重建 parent_id"。
- 结论：两方案对版本链路都无需改快照格式，方案 B 无额外版本成本。

#### 3.1.4 Excel 往返

- **当前方案**：模板「字典定义」Sheet 无父级列 → **层级在导出时永久丢失**，跨环境复制字典只能用扁平形式。
- **方案 B（P3）**：加父级列 + 两遍法导入 + 树前序导出 → 层级可跨环境完整迁移。

#### 3.1.5 多标准复用（易被忽视的放大效应）

全局字典（v2.9 拆分后）可被多个标准引用。字典是分类树时（地类/行业/资产类），**一份字典树供 N 个标准共享**，层级价值被 N 倍放大；当前方案下 N 个标准都只能吃扁平 code 集合。若字典只是枚举（性别/是否），多标准复用看不出区别。

#### 3.1.6 成本与风险

| | 当前方案 | 方案 B |
|---|---|---|
| 实现成本 | 0 | 迁移 + API 校验 + 质检 + Excel + 前端，跨 5 模块，分期 P1→P4 |
| 维护成本 | 0（没有校验逻辑可坏） | 双写 `parent_code`/`parent_id` 一致性维护（改 code 同步子项、导入回填） |
| 性能 | 最优（扁平一次取完） | 树查询需递归/CTE；字典数据量小（通常几十~几百条）可忽略 |
| 失败模式 | **静默**：脏数据无感知积累，爆在将来 | **显式**：操作被 400/409 拒绝，当场知道错 |
| 迁移风险 | 无（未改动） | 需兼容存量 `parent_code` + 旧 Excel，否则改坏现有数据 |

#### 3.1.7 现实例子

- **该用当前方案**：`性别{男,女}`、`是否{是,否}`、`文件类型{shp,gdb,geojson}`——扁平枚举，加层级是纯负担。
- **该用方案 B**：GB/T 21010 地类（一二三级嵌套）、国民经济行业分类、资产/设备分类树——树是数据的**本质形态**，且质检要按大类放行。

#### 3.1.8 决策结论

> **当前方案不是"错的"，它是"零约束"——优点是零成本零风险，缺点是用脏数据风险换来的；方案 B 是"有约束的树"——优点是数据自洽 + 质检语义升级 + 层级可复用可迁移，缺点是要为约束持续付费（双写一致性 + 严格校验的容错设计）。**
>
> 适用判定：**字典本身是树 → 方案 B；字典是枚举 → 当前方案；拿不准 → 至少补当前方案的校验缺口（假父 / 删父无保护，即方案 A 最小版），这不需要任何层级需求，防的是脏数据本身。**

## 4. 推荐方案 B 详细设计

### 4.1 数据模型

```python
# dictionary_items 迁移（alembic 0008_dict_item_parent）
parent_code: 保留（兼容既有数据 / 便于 Excel 往返与调试），加 Index
parent_id: 新增 String(36) FK → dictionary_items.id，nullable，ondelete="RESTRICT"
新增约束: 同字典内 parent 必须同 dict_id（应用层校验，DB 触发器可选）
```

- **为什么保留 `parent_code` 而非直接替换**：存量数据已有 parent_code 记录；Excel 导出/导入以 code 为稳定自然键（跨环境复制字典），`parent_id` 为内部引用；两者双写，以 `parent_code` 为真源，导入时按 code 解析出 id 后回填。
- **删除策略：`ondelete="RESTRICT"`**（有子项的父项禁止删除）——与业务语义一致（码值树不允许悬空），前端同时做软校验提前拦截。

### 4.2 API 变更

| 端点 | 变更 |
|------|------|
| `POST /dictionaries/{dict_id}/items`（批量添加） | 逐项校验：`parent_code` 存在且同字典；自引用拒绝；层级深度 ≤ 3（可配置）；`parent_code` 与 `item_code` 不可同值 |
| `PUT /dictionaries/{dict_id}/items`（批量更新） | 移除盲 `setattr`，改白名单字段 + 同上校验；`item_code` 变更需同步更新子项 `parent_code` 引用（或禁止改 code） |
| `DELETE /dictionaries/{dict_id}/items/{item_id}` | 有子项 → 409「存在子级条目，请先删除或转移子级」 |
| 字典详情 `GET`（可选增强） | `items` 附 `children` 树结构 或 前序平铺 + `depth` |

### 4.3 质检 A5（可选阶段 2）

- 现状：`dict_item_codes` 扁平集合，`value in allowed` 精确匹配。
- 增强：新增「父码通配」配置——字段字典关联 `filter_condition` 支持 `code_startswith` 语义（如允许 `A` 则 `A01`/`A02` 通过）。**默认关闭**，避免改变现有质检结果；仅当字段关联显式开启时生效。
- 兼容性：不开启通配的现有关联行为完全不变（回归零风险）。

### 4.4 Excel 往返（可选阶段 3）

- 模板「字典定义」Sheet 增加「父级编码」列（追加在「描述」之后，兼容旧列位）。
- 导出：按树前序排序输出，父项先于子项。
- 导入：**两遍法**——第一遍建全部字典项（暂存 code→临时 id），第二遍按父级编码回填 `parent_id`；父级编码缺失/未命中 → warning 记录并跳过（不失败，兼容旧文件）。

### 4.5 前端（可选阶段 3）

- 字典项表格：`parent_code` 列升级为父级下拉（同字典项选择）或只读展示（按 `item_code` 反查名称）。
- 树形视图（可选）：按 `parent_id` 递归渲染缩进/折叠；展开态 `sessionStorage` 记忆。
- 删除交互：有子项时前端先行拦截并提示「请先删除子级条目」。

## 5. 分期实施建议（将来启用时）

| 阶段 | 内容 | 验收 |
|------|------|------|
| P1 | 模型 + 迁移（parent_id FK + 索引）+ API 校验 + 删除保护 | 集成测试：父级不存在 400 / 自引用 400 / 深度超限 400 / 删父有子 409 / 正常建父子 201 |
| P2 | A5 父码通配（默认关闭） | 质检回归：未开通配结果与现状一致；开通配后子码命中 |
| P3 | Excel 模板列 + 两遍法导入 + 树前序导出 + 前端父级下拉/树渲染 | Excel 往返回环测试（导出→导入→树结构一致）+ Playwright UI |
| P4 | 源数据字典（`source_data.py`）同步启用（共用模型，校验函数抽公共工具） | 同 P1 用例跑源数据端点 |

## 6. 兼容性保证（任何阶段必须满足）

1. 存量字典项 `parent_code` 已填写的：导入后自动回填 `parent_id`，不丢数据
2. 现有 API 调用方不传 `parent_code`：行为与现状一致
3. 质检 A5 默认行为不变（通配默认关闭）
4. 旧版 Excel 文件（无父级列）仍可导入（列缺失按空处理）

## 7. 明确不做（本期边界）

- ❌ 多父（DAG）——无真实需求，方案 C 仅存档
- ❌ 父级码值跨字典引用——层级严格限定在单字典内
- ❌ 码值树的前端拖拽编排——先保证数据层正确，交互增强后置
